# M7: import radius in the user's unit (D23)

Spec: `docs/specs/2026-10-16-simplification-design.md` D23 **[F4]**, new: D32 / §9 Q12 (whole-metre precision, from the review).

## Design (built in M7-01, `6a71d9a`)

- Storage unchanged: `UserSettings.batch_import_radius` is **whole metres** (default 50). Everything that uses it
  (`groupPhotosByProximity`, `nearbySpots`, the nearby-spot offer) keeps working in metres.
- `src/utils/units.ts` converts at the edges, with the same `FEET_PER_METER = 3.28084` as `displayLength`:
  - `radiusToDisplay(meters, units)` → whole feet (Imperial) or metres (Metric): 50 → 164 ft / 50 m, 30 → 98 ft.
  - `radiusFromInput(text, units)` → whole metres, at least 1, or `null` for '', '0', negatives and non-numbers
    ('164' ft → 50, '100' ft → 30, '328' ft → 100, '1' ft → 1).
  - `radiusUnitLabel(units)` → 'ft' | 'm'.
- Profile (`app/(tabs)/profile.tsx`): label 'Import radius · ft|m', accessibilityLabel 'Import radius in feet|metres',
  `number-pad`. The field shows `radiusToDisplay(stored)`; a `draft` string exists only while typing, so a units switch
  or a store update re-renders it from the stored metres. Blur / Done with no draft or with the same metres writes
  nothing (no drift); invalid text drops the draft (the display comes back). Tapping Metric/Imperial commits the draft
  in the unit it was typed in first.
- Import (`app/import/index.tsx`): '(within 164 ft)' / '(within 50 m)'.

Whole feet and whole metres don't line up: each metre is ~3.28 ft, so some whole-foot values share a metre
(164 ft and 165 ft are both 50 m). Typing 165 ft stores 50 m and the field then shows 164. That snap of at most
2 ft is the D32 default (review #1, §9 Q12).

### Answers to the M7-02 question

**A stored radius that is not a whole number of feet round-trips without drift when the field is blurred unchanged:
yes.** `draft` (`profile.tsx` l.21-22) is `null` until the user types, and `commitRadius` returns at l.25 when it is,
so a plain blur parses and writes nothing. Second line of defence: for any whole-metre value the feet display is off
by ≤ 0.5 ft (0.15 m), so it reads back to the same metre and l.28's `!== batchRadius` skips the save; there is no
division result like 49.99 because `radiusFromInput` rounds to whole metres. Tests: "leaves the stored metres alone
when the field is blurred unchanged" (50 m shows 164, blur → 50, nothing saved), the new 50.4 m test above (isolates
the guard), and `utils.test.ts` "round-trips every whole-metre radius through its feet display" (1–500 m).
