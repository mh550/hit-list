Triggers (every trigger function `security definer` only where noted, `set search_path = ''`, fully qualified names):

- **rev**: `t20_rev` BEFORE INSERT OR UPDATE on `profiles, spots, media, hit_lists, hit_list_spots, hit_list_members`
  → `new.rev := nextval('public.sync_rev')`. A soft delete is an UPDATE, so it bumps rev. *Built (S3-02):*
  `public.bump_rev()` is **security definer**, and every role's privileges on `sync_rev` are revoked: Supabase's
  default grants give `authenticated` ALL on new sequences, which would let any user `setval` the pull cursor
  backwards.
- **updated_at guard (D48)**: `t10_stale_guard` BEFORE UPDATE on `spots, media, hit_lists`: `if new.updated_at <
  old.updated_at then return null` (the row is skipped, so `t20_rev` never fires: no rev bump). Equal is applied.
  Postgres fires same-event triggers in name order, hence the `t10`/`t20` prefixes.
- **profile on signup**: `on_auth_user_created` AFTER INSERT on `auth.users` → `insert into public.profiles (id)
  values (new.id)`; `security definer` (owned by postgres; the auth admin role inserts users).
- **D43 in one place**: `t30_member_spots_leave` AFTER DELETE on `hit_list_members` (`security definer`) → delete the
  list's `hit_list_spots` rows `added_by = old.user_id`. Leave, Remove, Decline and Stop sharing all go through it, so a
  direct DELETE can't leave a member's spots behind. *Built (S3-04)* as `public.remove_member_spots()`.
- **rev visibility (for S5, Opus review of S3-02, Important):** `nextval` runs before commit, so revs become
  visible out of order: A takes 100, B takes 101 and commits, a pull moves the cursor to 101, A commits and row 100 is
  never pulled by `rev > cursor`. S5 must handle it: e.g. pull only up to a rev no running transaction can still
  write (store `pg_current_xact_id()` beside rev and cap at `pg_snapshot_xmin(pg_current_snapshot())`), or re-read a
  safety window below the cursor. Not built in S3.
- Deletes of `hit_list_spots`/`hit_list_members` rows are hard deletes (no rev); how pull learns about them is S5's
  call (likely: refetch a list's membership when the list's rev moves; bump the parent list's rev from those
  triggers). Not built in S3.

Privileges in the schema migration: `alter default privileges in schema public revoke execute on functions from
public, anon;` and `revoke execute on all functions in schema public from public, anon;` so **anon can execute no
public function** (S3-08 asks). Each later migration grants `execute … to authenticated` (or `service_role`) per
function. *Built (S3-02):* PUBLIC's EXECUTE is a **global** default, which an `in schema` revoke cannot remove (a probe
function still had anon EXECUTE), so the migration runs `alter default privileges revoke execute on functions from
public;` (postgres's own functions only; extension functions belong to `supabase_admin` and keep theirs, checked:
anon can still run `extensions.st_makepoint`) plus `… in schema public revoke execute on functions from anon,
authenticated;`. So **a new `public` function starts with EXECUTE for nobody but its owner and `service_role`**
(Supabase's default for the `supabase_admin`-owned schema ACL), and **every later migration must `grant execute …
to authenticated` for each client-callable function** (and `revoke … from service_role` is not needed: it bypasses
RLS anyway). 010 proves it with a probe function. TRUNCATE (not covered by RLS) is revoked from anon/authenticated
on every table and by default for later ones; nobody but the trigger has a privilege on `sync_rev`.

## Row policies (S3-03…S3-07; all `to authenticated`; `anon` gets none)

- `spots`: SELECT `owner_id = (select auth.uid()) or can_read_spot(id)`; INSERT check `owner_id = auth.uid()`;
  UPDATE using/check `owner_id = auth.uid()`; **no DELETE** (soft delete is an UPDATE; account deletion runs as the
  service role, S4).
- `media`: SELECT own, or `deleted_at is null` and `can_read_spot(spot_id)`; INSERT check own + own spot; UPDATE own.
  *Built (S3-03):* `t05_keep_identity` BEFORE UPDATE triggers keep a spot's `id`/`owner_id`/`created_at` and a
  photo's `id`/`spot_id`/`owner_id`/`created_at` fixed.
- `hit_lists`: SELECT owner, or any membership row (an invitee sees name and owner; the spot count is not exposed:
  `hit_list_spots` needs `'member'`); INSERT check `owner_id = auth.uid()`; UPDATE owner only; no DELETE (soft).
- `hit_list_spots`: SELECT owner, or `'member'` while the list is shared and live (`can_read_list_spots`, S3-04); INSERT check **`added_by = auth.uid()` and the caller owns
  the spot** and (list owner or `'member'` with role `'add'`) and the list is live and manual. *This applies to the
  owner too*: otherwise any user could make another rider's spot readable by putting its id in their own shared list
  (§3.3 "you can't put someone else's spot in a list"). DELETE `added_by = auth.uid()` or list owner (D42).
- `hit_list_members`: SELECT the owner, the row's own user, and `'member'`s of the list (member strip); INSERT owner
  only, the invitee must be an accepted friend and must not have blocked the owner (D50), `status = 'invited'`;
  UPDATE owner (role) or own row; a `t10_member_guard` BEFORE UPDATE trigger lets a non-owner change only `status`
  `'invited'` → `'member'` (sets `joined_at`); DELETE owner or own row (D43 trigger fires either way).
- `profiles`: SELECT `id = auth.uid()` or `can_read_profile(id)` (security definer: accepted friend, a friendship row
  in either direction (a request's sender shows in the Inbox), or co-members: both `'member'`, owner ↔ member, and an
  invitee ↔ the list owner); UPDATE own row, check `id = auth.uid()` (id can't change); no INSERT/DELETE.
- `friendships`: SELECT where caller is `user_a` or `user_b`; DELETE same (Remove friend); writes only via functions.
- `blocks`: SELECT/DELETE `blocker = auth.uid()` only (the blocked user sees nothing); INSERT via `block_user`.
- `sends`: SELECT sender, or recipient while `withdrawn_at is null` and the recipient hasn't blocked the sender;
  no direct INSERT/UPDATE/DELETE (functions only, so the recipient can't change `payload`). *Built (S3-06):*
  `(sender = auth.uid() or recipient = auth.uid()) and can_read_send(id)` (the first half only lets the sender and
  recipient indexes serve a pull).
- `links`: RLS on, **no policies at all**.

## Storage (S3-06)

- Bucket: `insert into storage.buckets (id, name, public) values ('photos', 'photos', false) on conflict do nothing`
  (in the migration).
- Paths: `<owner_id>/<spot_id>/<media_id>.jpg` and `sends/<send_id>/<media_id>.jpg`. Exactly three segments; a helper
  `photo_path_ok(name)` rejects anything else and `try_uuid(text)` returns NULL instead of raising on a bad uuid.
- `storage.objects` policies (bucket `photos` only): SELECT `split_part(name,'/',1) <> 'sends' and
  can_read_spot(try_uuid(split_part(name,'/',2)))`, or `'sends'` prefix and the caller is the send's sender or (not
  withdrawn) recipient; INSERT/UPDATE/DELETE: first segment = `auth.uid()::text` and the caller owns that spot, or
  `'sends'` prefix and the caller is the send's sender. A removed member's SELECT is empty on the next query because
  `can_read_spot` is evaluated per query (no cache, no copy).
- *Built (S3-06, `20261023031134_sends_storage.sql`):* policies `photos_select/insert/update/delete` on
  `storage.objects` (bucket `photos` only; no other bucket has one) call two definer helpers. **Read**
  (`can_read_photo`): a send photo if `can_read_send`; a spot photo if the first segment is the caller (the owner
  reads everything under their prefix: a photo uploads before its media row, S5), or else the first segment is the
  spot's owner, a **live media row** with that id is on that spot (a removed photo is gone for members, as in
  `media_select`) and `can_read_spot`. **Write** (`can_write_photo(name, op)`): own prefix and own spot, any op. A
  send's photos are the sender's and **write-once** (D40, Opus review): insert only while the send is neither
  withdrawn nor saved, never an update (overwrite or move), delete until it is saved (a withdrawn send's photos can
  go). So S7's Save must call `mark_send_saved` before copying the photos.
  An UPDATE's new row must also pass the SELECT policy (Postgres), so a move needs read and write on both names. The
  bucket is `image/jpeg` only with a 10 MB limit (D46 re-encodes to JPEG ≤ 2048 px); the insert's `on conflict`
  resets an existing bucket to private with those limits. Direct `DELETE` on
  `storage.objects` raises unless `storage.allow_delete_query` is set (Supabase's `protect_objects_delete`; the
  Storage API sets it, 070 sets it before its delete cases).
- For S7 (Send's server-side photo copy): Storage `copy` needs SELECT on the source and INSERT on the target, so the
  sender copies `<self>/<spot>/<media>.jpg` → `sends/<send>/<media>.jpg` and a recipient's Save copies
  `sends/<send>/…` → `<self>/<new spot>/…` (after inserting the spot) under these policies as they are.

## pgTAP harness

- Files: `supabase/tests/NNN-<topic>.test.sql`, each `begin; select plan(n); … select * from finish(); rollback;`, so
  every file starts from the migrated, seeded database and leaves nothing behind. `supabase test db` installs pgTAP
  itself (probe above).
- **`supabase/seed.sql`** creates `schema tests` (`grant usage … to authenticated, anon, service_role`) with:
  - `tests.create_user(email text, username text default null) returns uuid`: inserts into `auth.users` (`id =
    gen_random_uuid()`, `aud`/`role` `'authenticated'`, `email`, `created_at`), which fires the profile trigger, then
    sets the username if given; returns the id.
  - `tests.authenticate_as(uid uuid)`: `set_config('role', 'authenticated', true)` and `set_config('request.jwt.claims',
    json_build_object('sub', uid, 'role', 'authenticated')::text, true)`.
  - `tests.authenticate_as_service_role()`: role `service_role`, claims `{"role":"service_role"}` (for `preview_link`).
  - `tests.clear_auth()`: role `anon`, claims cleared (for "anon can't" cases). Setup between steps uses plain `reset
    role;` (back to `postgres`, RLS bypassed).
- **Why seed.sql:** it runs only on `supabase start` (fresh volume) and `supabase db reset`, and `supabase db push`
  never sends it, so the test helpers can't reach a cloud database.
- RED first: each build feature commits its test file with the migration absent (the run's failures are recorded in
  Review with the commit hash), then commits the migration.

## Proposed changes to later features

- *Done in S3-05.* S3-05 (D50): a pending invitation from someone the invitee has since blocked should disappear (`block_user` can
  delete the `'invited'` rows between the two, both directions; the policies here don't look at blocks after the
  invite).
- S3-07: `redeem_invite` runs as the definer, so `guard_member_update` doesn't limit it; it must upgrade an `'invited'`
  row by an UPDATE of `status` (that fires the Join clean-up) or, for a new row, delete leftover `hit_list_spots`
  rows of that user itself; and it must refuse an unshared or deleted list like Join does.
- S3-03: add `area member reads no spot the filters exclude` (the policy applies `area_filters`, so it needs a test).
- S3-04: add `owner cannot add a spot they do not own` (the insert policy above requires spot ownership for everyone).
- S3-04 (S3-03 review): make `hit_lists.owner_id` and `kind` immutable and test it (`can_read_spot`'s area branch trusts
  `owner_id`).
- S5 (S3-03 review): index `rev` on synced tables; a push upsert must not change a spot's or photo's identity columns.
- *Done in S3-06.* S3-06 (D50): the sends SELECT policy must hide a send from a recipient who blocked its sender, and `create_send`
  should take `lock_user_pair` like `block_user` (same race as the invite one fixed in S3-05).
- S3-07: `redeem_invite` inserts through `t05_block_guard`, so a blocked user's redeem raises
  `'blocked users cannot be added…'`; catch it and raise the same `'invalid invite'` as the other cases.
- S4 (S3-06 review): `account-delete` must list the account's send ids and remove `sends/<id>/` objects before the
  profile goes (the cascade deletes the rows; the paths don't name the sender). S5: upload photos with
  `contentType: 'image/jpeg'` (the bucket allows only that). S7: Save = `mark_send_saved` first, then copy
  `sends/<id>/…` into the recipient's own prefix (send photos are write-once and the sender can't delete them after
  Save).
- S4: a username change through a rate-limited function would close the "blocked user probes a username" gap (§9
  Q19). S5: `readable_profile_ids()` if the profile pull is slow. S6: rate-limit friend requests.
