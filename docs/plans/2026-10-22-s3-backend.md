## Schema (S3-02: `supabase/migrations/<ts>_schema.sql`, one file)

Extensions: `create extension if not exists postgis with schema extensions;` `citext` (same schema). `pgcrypto` is
already installed in `extensions` on Supabase (used by S3-07 as `extensions.digest`).

Sync counter: `create sequence public.sync_rev;` one counter for every synced table, so a pull cursor is one number
and "a hit_lists insert gets a rev greater than the last spots rev" holds.

Triggers (every trigger function `security definer` only where noted, `set search_path = ''`, fully qualified names):

- **rev**: `t20_rev` BEFORE INSERT OR UPDATE on `profiles, spots, media, hit_lists, hit_list_spots, hit_list_members`
  → `new.rev := nextval('public.sync_rev')`. A soft delete is an UPDATE, so it bumps rev.
- **updated_at guard (D48)**: `t10_stale_guard` BEFORE UPDATE on `spots, media, hit_lists`: `if new.updated_at <
  old.updated_at then return null` (the row is skipped, so `t20_rev` never fires: no rev bump). Equal is applied.
  Postgres fires same-event triggers in name order, hence the `t10`/`t20` prefixes.
- **profile on signup**: `on_auth_user_created` AFTER INSERT on `auth.users` → `insert into public.profiles (id)
  values (new.id)`; `security definer` (owned by postgres; the auth admin role inserts users).
- **D43 in one place**: `t30_member_spots_leave` AFTER DELETE on `hit_list_members` (`security definer`) → delete the
  list's `hit_list_spots` rows `added_by = old.user_id`. Leave, Remove, Decline and Stop sharing all go through it, so a
  direct DELETE can't leave a member's spots behind. *Written in S3-04 with its tests.*
- Deletes of `hit_list_spots`/`hit_list_members` rows are hard deletes (no rev); how pull learns about them is S5's
  call (likely: refetch a list's membership when the list's rev moves; bump the parent list's rev from those
  triggers). Not built in S3.

Privileges in the schema migration: `alter default privileges in schema public revoke execute on functions from
public, anon;` and `revoke execute on all functions in schema public from public, anon;` so **anon can execute no
public function** (S3-08 asks). Each later migration grants `execute … to authenticated` (or `service_role`) per
function.

## Functions (S3-03…S3-07)

Every one: `language plpgsql` or `sql`, **`security definer`, `set search_path = ''`**, every name schema-qualified,
checks `auth.uid()` (raises `'not signed in'` when NULL), `revoke … from public, anon`, `grant execute … to
authenticated` unless noted. Helpers used inside policies are `stable` and also security definer, which is what stops
policy recursion (profiles ↔ hit_list_members ↔ hit_lists).

## Row policies (S3-03…S3-07; all `to authenticated`; `anon` gets none)

- `spots`: SELECT `owner_id = (select auth.uid()) or can_read_spot(id)`; INSERT check `owner_id = auth.uid()`;
  UPDATE using/check `owner_id = auth.uid()`; **no DELETE** (soft delete is an UPDATE; account deletion runs as the
  service role, S4).
- `media`: SELECT `can_read_spot(spot_id)` and (`deleted_at is null` or own); INSERT check own + own spot; UPDATE own.
- `hit_lists`: SELECT owner, or any membership row (an invitee sees name and owner; the spot count is not exposed:
  `hit_list_spots` needs `'member'`); INSERT check `owner_id = auth.uid()`; UPDATE owner only; no DELETE (soft).
- `hit_list_spots`: SELECT owner or `'member'` of the list; INSERT check **`added_by = auth.uid()` and the caller owns
  the spot** and (list owner or `'member'` with role `'add'`) and the list is live and manual. *This applies to the
  owner too*: otherwise any user could make another rider's spot readable by putting its id in their own shared list
  (§3.3 "you can't put someone else's spot in a list"). DELETE `added_by = auth.uid()` or list owner (D42).
- `hit_list_members`: SELECT the owner, the row's own user, and `'member'`s of the list (member strip); INSERT owner
  only, the invitee must be an accepted friend and must not have blocked the owner (D50), `status = 'invited'`;
  UPDATE owner (role) or own row; a `t10_member_guard` BEFORE UPDATE trigger lets a non-owner change only `status`
  `'invited'` → `'member'` (sets `joined_at`); DELETE owner or own row (D43 trigger fires either way).
- `profiles`: SELECT `id = auth.uid()` or `can_read_profile(id)` (security definer: accepted friend, a friendship row
  in either direction (a request's sender shows in the Inbox), or co-members: both `'member'`, owner ↔ member, and an
  invitee ↔ the list owner); UPDATE own row, check `id = auth.uid()` (id can't change); no INSERT/DELETE.
- `friendships`: SELECT where caller is `user_a` or `user_b`; DELETE same (Remove friend); writes only via functions.
- `blocks`: SELECT/DELETE `blocker = auth.uid()` only (the blocked user sees nothing); INSERT via `block_user`.
- `sends`: SELECT sender, or recipient while `withdrawn_at is null` and the recipient hasn't blocked the sender;
  no direct INSERT/UPDATE/DELETE (functions only, so the recipient can't change `payload`).
- `links`: RLS on, **no policies at all**.

## Storage (S3-06)

- Bucket: `insert into storage.buckets (id, name, public) values ('photos', 'photos', false) on conflict do nothing`
  (in the migration).
- Paths: `<owner_id>/<spot_id>/<media_id>.jpg` and `sends/<send_id>/<media_id>.jpg`. Exactly three segments; a helper
  `photo_path_ok(name)` rejects anything else and `try_uuid(text)` returns NULL instead of raising on a bad uuid.
- `storage.objects` policies (bucket `photos` only): SELECT `split_part(name,'/',1) <> 'sends' and
  can_read_spot(try_uuid(split_part(name,'/',2)))`, or `'sends'` prefix and the caller is the send's sender or (not
  withdrawn) recipient; INSERT/UPDATE/DELETE: first segment = `auth.uid()::text` and the caller owns that spot, or
  `'sends'` prefix and the caller is the send's sender. A removed member's SELECT is empty on the next query because
  `can_read_spot` is evaluated per query (no cache, no copy).

## pgTAP harness

- Files: `supabase/tests/NNN-<topic>.test.sql`, each `begin; select plan(n); … select * from finish(); rollback;`, so
  every file starts from the migrated, seeded database and leaves nothing behind. `supabase test db` installs pgTAP
  itself (probe above).
- **`supabase/seed.sql`** creates `schema tests` (`grant usage … to authenticated, anon, service_role`) with:
  - `tests.create_user(email text, username text default null) returns uuid`: inserts into `auth.users` (`id =
    gen_random_uuid()`, `aud`/`role` `'authenticated'`, `email`, `created_at`), which fires the profile trigger, then
    sets the username if given; returns the id.
  - `tests.authenticate_as(uid uuid)`: `set_config('role', 'authenticated', true)` and `set_config('request.jwt.claims',
    json_build_object('sub', uid, 'role', 'authenticated')::text, true)`.
  - `tests.authenticate_as_service_role()`: role `service_role`, claims `{"role":"service_role"}` (for `preview_link`).
  - `tests.clear_auth()`: role `anon`, claims cleared (for "anon can't" cases). Setup between steps uses plain `reset
    role;` (back to `postgres`, RLS bypassed).
- **Why seed.sql:** it runs only on `supabase start` (fresh volume) and `supabase db reset`, and `supabase db push`
  never sends it, so the test helpers can't reach a cloud database.
- RED first: each build feature commits its test file with the migration absent (the run's failures are recorded in
  Review with the commit hash), then commits the migration.
