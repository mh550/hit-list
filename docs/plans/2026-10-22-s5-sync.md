# S5 plan: sync the rider's own spots, photos and hit lists

> **For agentic workers:** one harness session per feature (S5-02 … S5-09); each build feature commits its test file
> **RED first** (`S5-0n: RED …`, first run fails, note the failure in the message), then the code that makes it pass.

**Goal:** a signed-in rider's spots, photos and hit lists back up to their account and arrive on a second phone; the
first sign-in adopts what is already on the phone; signing out asks Keep / Remove; another account on the same phone
never sees them; a failed sync never loses a spot or a photo.

**Architecture:** migration 5 adds `owner_id`/`rev` (and media `updated_at`/`deleted_at`), `sync_outbox`,
`sync_state` and **SQLite triggers that append the outbox row inside the writing statement** (no app-level
transaction, see Outbox). `src/sync/push.ts` drains the outbox in id order (photos re-encoded and uploaded before their
media row); `src/sync/pull.ts` pages each table by the server's `rev`; `src/sync/engine.ts` runs push → pull →
photo downloads single-flight; `src/sync/adopt.ts` owns sign-in adoption, the account switch and Remove.

**Tech stack:** `@supabase/supabase-js` 2.118 (postgrest-js, storage-js `upload`/`download`), `expo-image-manipulator`
~57.0.21 (installed in S5-01, chore `5cc9e8f`), `expo-file-system` 57, expo-sqlite 57; local Supabase CLI (S3).

**Spec:** §1 Ownership, §3.2–§3.4, §7 S5, D38, D46, D48, D51, D62, D65–D69 (new). **Diff base for the S5-09 review:
`7be863a`** (HARNESS: S4 verified).

## Global constraints

- Push and pull run only with a session (`getSupabase()` non-null and `auth.getSession()` has one); signed out or
  unconfigured they resolve and do nothing. Nothing on a screen waits for the network.
- **Never lose a row:** an outbox row is deleted only after the server confirmed the write; a pull never overwrites
  a local row whose `updated_at` is newer; Remove from this phone is offered only when nothing is pending.
- Timestamps: the server answers `2026-10-23T01:02:03.456789+00:00`, the app writes `…Z`. One tested helper
  `src/sync/time.ts` `toIso(x): string | null` (handles `+00:00`, 0–6 fraction digits, `YYYY-MM-DD HH:MM:SS`; null when
  unreadable; never `Date.parse` alone, Hermes rejects some of these) for every compare and every value pull stores or
  push sends (`captured_at` unreadable → null). Never compare raw strings across the boundary.
- Server errors are `console.warn` (Jest's zero `console.error` rule); the UI shows counts and fixed copy only.
- PostgREST caps a response at 1000 rows: every list query pages (`.range()` or `limit 500` + `rev` cursor).
- `npx expo lint && npx tsc --noEmit && npx jest --silent` green after every feature.

## Outbox (S5-02) — triggers + `src/db/sync.ts`

**Why triggers:** CLAUDE.md forbids `withTransactionAsync` for app writes (a plain BEGIN/COMMIT on the one shared
connection: a concurrent write joins or breaks it). A trigger's insert is part of the writing statement, so the row
and its outbox entry commit or fail together with no BEGIN; every existing db function gets this for free.

**Rule:** an outbox row is appended when the row belongs to the phone's account (`owner_id = (SELECT value FROM
sync_state WHERE key = 'user_id')`, written `= me` below; a membership: its list **and** its spot are `me`'s) **and
the write did not come from a pull**. Others' rows (S8) and phone-only rows (NULL) never queue. A pull always writes the server's `rev` (strictly greater than what is
stored); the app never writes `rev`. So:

| Trigger | Fires | Appends |
|---|---|---|
| `spots_outbox_ins` AFTER INSERT ON spots | `NEW.owner_id = me AND NEW.rev IS NULL` | `('spot', NEW.id, 'upsert')` |
| `spots_outbox_upd` AFTER UPDATE ON spots | `NEW.owner_id = me AND NEW.rev IS OLD.rev` | `'delete'` when `OLD.deleted_at IS NULL AND NEW.deleted_at IS NOT NULL`, else `'upsert'` |
| `media_outbox_ins` / `_upd` | same on media | `('media', id, …)` same op rule |
| `hit_lists_outbox_ins` / `_upd` | same on hit_lists | `('hit_list', id, …)` same op rule |
| `hit_list_spots_outbox_ins` AFTER INSERT | `NEW.rev IS NULL` and list owner `= me` and spot owner `= me` | `('hit_list_spot', list/spot, 'upsert')` |
| `hit_list_spots_outbox_del` AFTER DELETE | list and spot `= me` and `OLD.rev IS NOT -1` | `('hit_list_spot', list/spot, 'delete')` |

So: `insertSpot`/`updateSpot`/`softDeleteSpot`, `insertMedia`/`deleteMedia`, `insertHitList`/`updateHitList`/
`softDeleteHitList`, `addSpotsToList` (one row per inserted spot; `INSERT OR IGNORE` skips existing ones, so no row)
and `removeSpotFromList` append exactly one row each (memberships: one per spot), adoption's `UPDATE … SET owner_id`
appends an `'upsert'` per row, and pull (writes `rev`) appends nothing. Every delete that is not the rider's (pull's
membership reconciliation, Remove, the account switch) first sets `rev = -1` on the rows (hit_list_spots has no update
trigger) or runs after `user_id` changed, so it queues nothing: a queued DELETE would remove server data.

**Who sets owner_id on new rows:** `currentOwnerId()` in `src/sync/owner.ts` = the sync store's `adoptedUserId`
(set by `adopt` once `sync_state.user_id` = the signed-in uid; cleared on sign-out), else `undefined`: a row made in the
moment between sign-in and adoption stays NULL and adoption takes it. `useSpotActions.createSpot` and `useHitListActions.createList` pass it;
`insertMedia` writes `owner_id = (SELECT owner_id FROM spots WHERE id = ?)` (a photo belongs to its spot's owner,
also while signed out after Keep). Edits to an owned row made while signed out queue under that owner and push when
they sign back in.

**`src/db/sync.ts`** (real SQLite tests, `db-sync.test.ts`):

```ts
export type OutboxEntity = 'spot' | 'media' | 'hit_list' | 'hit_list_spot';
export type OutboxOp = 'upsert' | 'delete';
export interface OutboxRow { id: number; entity: OutboxEntity; entity_id: string; op: OutboxOp; created_at: string;
  attempts: number; last_error?: string }
export function enqueue(db, entity: OutboxEntity, entityId: string, op: OutboxOp, at?: string): Promise<void>;
export function adoptableMemberships(db): Promise<string[]>;          // 'list/spot' of live lists where the list or
                                                                       // the spot is still NULL-owned (read BEFORE adopting)
export function enqueueMemberships(db, ids: string[]): Promise<void>;  // adopt: one 'upsert' each, after the spots
export function peekOutbox(db, limit: number, opts?: { skipFailed?: boolean; minAttempts?: number;
  maxAttempts?: number }): Promise<OutboxRow[]>;                        // id order; skipFailed = attempts < 3
export function markDone(db, id: number): Promise<void>;                // DELETE the row
export function markFailed(db, id: number, error: string): Promise<void>; // attempts += 1, last_error
export function countPending(db): Promise<number>;                      // every row not parked
export function countFailed(db): Promise<number>;                       // attempts >= 10, not parked
export function parkRow(db, id: number, error: string): Promise<void>;  // permanent failure, see Push
export function resetFailed(db): Promise<void>;                         // attempts = 0, last_error NULL where >= 10
export function clearOutbox(db): Promise<void>;
export function getCursor(db, table: SyncTable): Promise<number>;       // 0 by default
export function setCursor(db, table: SyncTable, rev: number): Promise<void>;
export function resetCursors(db): Promise<void>;
export function getSyncState(db, key: string): Promise<string | undefined>;
export function setSyncState(db, key: string, value: string | null): Promise<void>; // null deletes the key
```

Town backfill (`useSpotActions`' `generated_name`) passes the spot's current `updated_at`, so it never outranks a
newer edit made on another phone (the server's stale guard drops it when the server is newer).

No de-duplication: three edits = three rows; each push reads the row's **current** state, so later rows re-send the
same values (cheap; the server applies equal `updated_at`). De-duplicating safely needs an in-flight marker; not worth it.

## Push (S5-03) — `src/sync/push.ts`, `src/sync/photos.ts`

`push(db, client, uid, io = defaultPhotoIO): Promise<{ pushed: number; failed: number }>`

1. **Fresh pass:** `peekOutbox(db, 50, { skipFailed: true })` repeatedly; push each row in order; on the **first
   failure** `markFailed` and stop this pass (later rows wait: a membership must not reach the server before its spot).
2. **Backoff pass:** rows with `3 ≤ attempts < 10`, each tried once per sync, a failure doesn't stop the pass.
3. Rows with `attempts ≥ 10` wait for Profile's Retry (`resetFailed`). Nothing is ever deleted unconfirmed.
4. **Permanent failures are parked**, not retried: PostgREST `42501` (RLS: e.g. a membership of a list another phone
   deleted), `23514` (check), and `'photo missing'`. `parkRow` sets `parked = 1` + `last_error`, `console.warn`s; parked
   rows don't block the fresh pass, don't count in `countPending`/`countFailed` (so they never block Remove or an account
   switch) and are cleared with the outbox. `23503` (FK: the spot isn't there yet) stays a normal failure.

Per row (an upsert reads the local row now; a row that no longer exists locally is `markDone`, nothing to send):

| entity | server call | payload (local → server) |
|---|---|---|
| spot | `from('spots').upsert(row)` | `id, owner_id, name, generated_name, lat ← latitude, lng ← longitude, feature_types ← JSON.parse(feature_types_json)` (text[]), `stopped ← stopped === 1, natural_speed` (0 stays 0, NULL → null), `notes, primary_photo_id, created_at, updated_at, deleted_at` (null when live). `legacy_json` never leaves the phone (D68). |
| media | photo first (below), then `from('media').upsert(row)` | `id, spot_id, owner_id, storage_path = '<owner>/<spot>/<media>.jpg', captured_at, lat, lng, uploaded_by = owner_id, created_at, updated_at, deleted_at`. A deleted media row skips the upload. |
| hit_list | `from('hit_lists').upsert(row)` | `id, owner_id, name, kind, area_center_lat/lng, area_radius_m, area_filters ← JSON.parse(area_filters_json), area_place, shared ← shared === 1, created_at, updated_at, deleted_at` |
| hit_list_spot upsert | `from('hit_list_spots').upsert(row, { onConflict: 'list_id,spot_id', ignoreDuplicates: true })` | `list_id, spot_id, added_by = uid, added_at` (there is no update policy, so `ON CONFLICT DO NOTHING`) |
| hit_list_spot delete | `from('hit_list_spots').delete().eq('list_id', l).eq('spot_id', s)` | — (0 rows deleted = done) |

A spot or list `'delete'` is the same upsert (the row carries `deleted_at`; there is no delete policy on spots, media or
hit_lists). The server's `t10_stale_guard` skips an older `updated_at` (equal applies), which is LWW on the server side.
Success → `markDone`. `{ error }` or a throw → `markFailed(row.id, error.message)`, `console.warn('[sync] push …')`.

**Photos (`src/sync/photos.ts`, D46):**

```ts
export interface PhotoIO {                       // injectable: Jest fakes it, the integration test passes Node's fs
  exists(relativePath: string): boolean;
  prepare(relativePath: string): Promise<{ uri: string; bytes: Uint8Array; cleanup(): void }>;
  write(relativePath: string, bytes: Uint8Array): void;  // own photos pulled from another phone (Paths.document)
  remove(relativePath: string): void;
}
export function preparePhoto(localUri: string): Promise<{ uri: string; bytes: Uint8Array }>;
export function uploadPhoto(client, owner: string, media: Media, bytes: Uint8Array): Promise<string>; // storage path
export function downloadMissingPhotos(db, client, uid, io, limit = 20): Promise<number>;
```

- `preparePhoto`: `ImageManipulator.manipulate(uri)` → `renderAsync()` (an `ImageRef` with `width`/`height`); if the
  long edge > 2048, `context.resize(w >= h ? { width: 2048 } : { height: 2048 })` and render again; `saveAsync({
  compress: 0.85, format: SaveFormat.JPEG })` writes a **new file in the cache directory**; bytes read from that file;
  `cleanup` deletes it. The original under `Paths.document/photos` is never opened for writing. (Members cited from
  `node_modules/expo-image-manipulator/build/{ImageManipulator.types,ImageManipulatorContext,ImageRef}.d.ts`.)
- `uploadPhoto`: `storage.from('photos').upload('<owner>/<spot>/<media>.jpg', bytes, { contentType: 'image/jpeg',
  upsert: true })` (upsert: a retry after a failed row upsert re-uploads harmlessly).
- Local file missing (`!io.exists(file_path)`) → `parkRow(id, 'photo missing')` and go on (nothing to upload, ever).
- `downloadMissingPhotos` (S5-04 calls it, engine runs it after pull): own live media whose file is missing →
  `storage.from('photos').download('<owner_id>/<spot_id>/<id>.jpg')` (local media has no storage_path column; the
  path is always derived) → `blob.arrayBuffer()` → `io.write(file_path, bytes)`; sequential,
  ≤ 20 per sync; failures warn and retry next sync. Others' photos (S8) go to `Paths.cache` lazily, not here.

### As built (S5-03)

- `push(db, client, uid, io = defaultPhotoIO)` → `{ pushed, failed }`; runs only when `auth.getSession()` is `uid`
  **and** `sync_state.user_id = uid`. Both passes page by id (`peekOutbox` gained `afterId`). The fresh pass stops at
  its first failure, and the backoff pass is skipped then.
- **Waiting (review #1, Critical):** a media or `hit_list_spot` upsert whose spot (or list) still has an earlier,
  unparked outbox row is left untouched, with no attempt and no call, until that row is done. The server answers a
  missing parent with **42501** (RLS runs before the FK), not 23503. Without the wait, the row would be parked for good.
- **42501 re-checks the session (review #3):** with no session, or another rider's, the push stops and leaves the row
  as it was. Otherwise the row is parked. Parked: 42501, 23514, `'photo missing'`, `'not this account'` (a queued row
  whose `owner_id` ≠ uid). Feature step "marked failed with last_error 'photo missing'" = `parkRow`, as the plan says.
- **`shared` is never pushed (review #4):** a stale `false` would fire `t30_unshare` and drop every member. Only
  the sharing functions (S7/S8) change it, and PostgREST's upsert updates only the columns sent.
- `captured_at` is EXIF wall-clock time with no zone (`src/utils/exif.ts`). Push reads it as phone-local time
  (`toIso(x, 'local')`, review #2). Every other zoneless value is UTC (SQLite `datetime()`). Required timestamps
  toIso fails to read are sent as stored, never invented.
- `PhotoIO` has `exists`/`prepare` only; S5-04 adds `write`/`remove` for downloads. `preparePhoto` releases the
  context and every `ImageRef` and deletes its cache copy if the read fails.
- Left open (Minor, review #6): `uploadPhoto` drops the storage `statusCode`, so a storage refusal no retry can fix
  is retried up to 10 times. With the waiting rule a 403 no longer comes from a missing spot, so parking 403 is now
  safe. That is left to S5-09.

## Pull (S5-04) — `src/sync/pull.ts`

`pull(db, client, uid, io): Promise<{ changed: boolean }>`, tables in FK order: `spots`, `media`, `hit_lists`,
`hit_list_spots`.

1. Per table: `from(t).select('*').gt('rev', cursor - REV_OVERLAP).order('rev').limit(500)` (`REV_OVERLAP = 200`:
   `bump_rev` takes `nextval` inside the writer's transaction, so rev 100 can commit after rev 101; re-reading a short
   window catches it, and applying a row twice is a no-op); apply rows in order; **stop the table at the first row
   that fails** and `setCursor(t, rev of the last row applied)` (the rest come next sync, after their spot has arrived);
   a full page of 500 with no failure → next page. A first pull (cursor 0) uses `gt('rev', 0)`.
2. **Apply a row** (one statement each, no transaction; all write `rev`, so no outbox row):
   - absent locally → `INSERT` with `owner_id`, `rev`, mapped columns (`feature_types` → `feature_types_json`,
     `lat/lng` → `latitude/longitude`, `shared` → 0/1, `area_filters` → JSON text, `natural_speed` null → NULL,
     timestamps normalised). Media gets `file_path = 'photos/<spot>/<media>.jpg'` (the file comes from
     `downloadMissingPhotos`).
   - present → `UPDATE … WHERE id = ? AND (rev IS NULL OR rev < ?)` only if `Date.parse(incoming.updated_at) ≥
     Date.parse(local.updated_at)`; otherwise skip (an unpushed local edit wins; its outbox row still pushes it).
     A row with `deleted_at` soft-deletes locally the same way (a spot's `hit_list_spots` rows stay).
   - `hit_list_spots`: `INSERT OR IGNORE` with `rev`; an FK failure (spot or list not here) stops the table (above).
   - `changed = true` for any row written.
3. **Membership reconciliation** (server deletes memberships for real, so `rev` can't show it): keyset-page
   `from('hit_list_spots').select('list_id,spot_id').order('list_id').order('spot_id')`; **any page error skips the
   whole step**; then for local memberships of my lists the server doesn't list **and with no outbox row**: set `rev =
   -1`, then delete (no outbox row, see Outbox).
4. **Readable-id reconciliation** (S8 needs it; S5 tests it): keyset-page `from('spots').select('id').order('id').gt('id', last)`
   (any page error skips the step); every local spot
   with `owner_id IS NOT NULL AND owner_id <> uid` not in the set is **removed** (`DELETE` its `hit_list_spots`,
   `media`, then the spot; spec §3.4 "removes local copies"), never a row owned by `uid` or a NULL owner. Spots and
   media have no delete trigger, so nothing is queued (a membership in one of my lists fires `_del`: the harmless echo
   above). Feature S5-04 step 2 says soft-delete; a soft delete is an UPDATE, which the update trigger would queue for a
   row this rider can't write, so the plan removes them (gone from `getSpots` either way; Proposed change in progress).

### As built (S5-04)

- `pull(db, client, uid)` → `{ changed }` (no `PhotoIO`: the engine, S5-05, calls `downloadMissingPhotos` after it).
  Same guard as push (`src/sync/account.ts` `maySync`: a session for `uid` **and** `sync_state.user_id = uid`).
  `PULL_PAGE = 500`, `REV_OVERLAP = 200`; the first page asks `gt('rev', max(0, cursor - 200))`, later pages
  `gt('rev', last rev of the page)`; the cursor only moves forward. A select error leaves that table as it was.
- **LWW in the statement (review #1, Important):** the UPDATE carries `rev < ?` **and** `julianday(updated_at) <=
  julianday(incoming)`, so an edit saved while the pull awaits is never overwritten. `changed` counts rows written
  whose values differ (the echo of the phone's own push only stores the rev: no store reload).
- Media inserts get `file_path = photos/<spot>/<media>.jpg`; an update keeps the local file_path. `captured_at` comes
  back as UTC `…Z` (push reads a zoned value as such). `shared` is pulled, never pushed.
- A membership the rider removed and hasn't pushed (a waiting `delete` row) is not re-inserted.
- **Reconciliation asks about local candidates only** (chunks of 100 ids in `.in()`, no full-table paging): memberships
  of the rider's live lists whose spot is synced (owner not NULL) with **no outbox row of any kind**; others' spots
  (`owner_id` not NULL and ≠ uid). Any failed request, or the session gone when the answers are in, removes nothing.
  Foreign unreadable spots are **deleted** (spot, media rows, memberships), not soft-deleted (Proposed change, S5-01).
  With no foreign spot on the phone the readable-id check asks nothing.
- `downloadMissingPhotos(db, client, uid, io, limit = 20)`: own live media of live spots with `rev` set and a relative
  `photos/…` path whose file is missing; newest first; a failure warns and retries next sync. `PhotoIO.write` makes the
  folder and writes. React Native's Blob has no `arrayBuffer()`, so bytes come through `FileReader.readAsArrayBuffer`.
- **Left for S8 (review #2, Important once sharing is live):** a row that can never be written stops its table for
  good (e.g. a shared list's membership whose spot the owner deleted: the membership stays readable, the spot does
  not; or a foreign spot removed by reconciliation that becomes readable again keeps its old rev). S8 needs a skip
  after N failures per (table, rev) or a readability check, and the "fetch readable ids not held locally" step (S3-08).
  Invitee-only lists (`hit_lists_select` returns them) are inserted as lists today; S7/S8 must filter them.
- Accepted (Minor/Nit): `sync_rev` is one sequence for every table and rider, so the 200 window is shared (commented);
  `downloadMissingPhotos` checks every candidate file each sync; a re-add between reconciliation's `rev = -1` and its
  DELETE (one await) is removed.

## Engine (S5-05) — `src/sync/engine.ts`, `src/stores/sync-store.ts`, `src/hooks/use-sync.ts`

- `syncNow(db): Promise<void>`: single-flight (a module-level promise; a second call returns the running one). No
  client, no session, or **`sync_state.user_id` ≠ the session's uid (not adopted yet, or a switch waiting for its
  confirm) → resolve without push or pull**. `adopt` and `removeLocalAccountData` run through the same single-flight
  queue (`runExclusive`), so no push or pull overlaps their transaction. Else `push` (caught: `console.warn`, pull still runs) → `pull` → `downloadMissingPhotos`
  → if `changed` or anything pushed changed ownership, reload the spots, media and hit-lists stores from the DB (the
  same loaders as `useDbInit`) → sync store `{ lastSyncAt, syncing, failedCount: countFailed, lastError }`.
- `useSync()` mounted once in `DBInitializer` after `useAuthInit`: when `isReady` and status `'signed_in'` →
  `syncNow`; AppState `'active'` → `syncNow`; `setInterval(syncNow, 300_000)` while active and signed in, cleared on
  `'background'`, sign-out and unmount.
- Spots tab: `refreshControl` (`RefreshControl refreshing={syncing} onRefresh={syncNow}`) only when signed in.
- Profile (signed in): `Backed up · just now` / `Backed up · 3 min ago` (`src/utils/relative-time.ts`); never synced
  yet → `Not backed up yet`; `failedCount > 0` → `3 changes not backed up` + `Retry` (`resetFailed` → `syncNow`).

## Adoption and account switch (S5-06) — `src/sync/adopt.ts`

`adopt(db, uid, io = defaultPhotoIO, opts?: { confirmSwitch?: boolean }): Promise<'done' | 'needs_confirm'>`:

1. `prev = getSyncState('user_id')`. If `prev` and `prev ≠ uid` (another account's rows are here):
   - `countPending(db) > 0` and no `confirmSwitch` → return `'needs_confirm'`, change nothing. `useAuthInit` alerts
     **"Changes not backed up"** · *"3 changes made on this phone haven't reached your last account. Signing in here
     removes them from this phone. To keep them, cancel and sign in with that account first."* · `Cancel` (signs this
     account out) · `Remove and continue` (destructive; calls `adopt` again with `confirmSwitch: true`). D66 *default*.
   - Switch (part of step 2's transaction): collect the spot ids owned by `prev`; delete `hit_list_spots` whose list
     or spot is `prev`'s, `media` and `spots` owned by `prev`, `hit_lists` owned by `prev` (`user_id` is still `prev`,
     so the membership deletes set `rev = -1` first); `clearOutbox`, `resetCursors`. After the commit, delete `photos/<spotId>/` for each collected spot (a failure warns).
2. **One `withTransactionAsync`** (skipped when there is no switch and nothing to adopt): the switch deletes above,
   `ids = adoptableMemberships(db)` (read before the updates), `setSyncState('user_id', uid)` (before the updates, so
   the triggers see `me`), `UPDATE spots/media/hit_lists SET owner_id = uid WHERE owner_id IS NULL` (the triggers queue
   the upserts, spots first), `enqueueMemberships(db, ids)` (after them). A failure rolls all of it back (owner_id
   NULL everywhere, outbox untouched). Idempotent: a second run finds no NULL owner, so no membership either.
3. Reload the stores, then `syncNow`.

Transactions here are the exception to the CLAUDE.md rule, accepted because they run only at sign-in (the sign-in
modal is up, no screen can write) or at launch when there is work (rare): the only writer that can overlap is the town
backfill (`generated_name`, redone on a later launch). `useAuthInit` calls `adopt` when the status becomes
`'signed_in'` and once at launch after `isReady` if already signed in.

## Sign out (S5-06) — D38, D62 ends, D69 *default*

Profile → `Sign out`: `await syncNow()` raced against a 10 s timeout (a last backup; offline it fails quietly) → `pending = countPending(db)`:

- `pending === 0`: Alert **"Keep spots on this phone?"** · *"They're backed up in your account either way."* ·
  `Keep` (sign out; rows keep `owner_id`, `sync_state.user_id` stays so the next account is detected) ·
  `Remove from this phone` (destructive: `removeLocalAccountData(db, uid, io)` in **one transaction** clears `user_id`
  first (nothing queues), deletes the rows owned by `uid` and their memberships, clears the outbox and cursors; after
  the commit deletes the photo files and reloads the stores; then signs out).
- `pending > 0`: Alert **"3 changes aren't backed up yet"** · *"Sign out anyway and they'll back up next time you sign
  in to this account."* · `Cancel` · `Sign out anyway` (= Keep). **No Remove.** (Feature S5-06 says `failedCount > 0`;
  pending includes failed and also catches offline edits. Proposed change in progress.)
- Delete account (D51, S4-05): after the function succeeds, Alert **"Your account is deleted. Keep the spots on this
  phone?"** · `Keep` (D67 *default*: `releaseAccountData(db, uid, io)` sets `owner_id = NULL` on the account's rows,
  deletes media rows whose file was never downloaded, clears outbox/cursors/`user_id`: they become phone-only spots a
  later sign-in adopts) · `Remove from this phone`.

## Review focus (S5-09)

Outbox row deleted only after a confirmed write · pull never overwrites a newer unpushed edit · Remove impossible with
pending rows · adopt atomic · timers cleared · re-encode never writes `Paths.document/photos` · reconciliation never
touches `uid`'s rows · push errors are `console.warn` · triggers never fire on pull writes (no echo loop: an echoed
