# S7 plan: Send (a one-time copy of spots to friends)

> **For agentic workers:** one harness session per feature (S7-02 … S7-08); each build feature commits its test file
> **RED first** (`S7-0n: RED …`, first run fails, note the failure in the message), then the code that makes it pass.

**Goal:** a signed-in rider sends one spot, a selection, a list's spots or an area result to friends as a **frozen
copy** (D40). The friend's Inbox shows it until they Save (all, into a new hit list, or picked spots) or Dismiss; a
saved spot is their own private spot reading 'From @ana'. Profile → Sent lists every send (Waiting · Saved ·
Withdrawn) with Withdraw until it is saved. The word is always **Send** with the paper-plane icon (D34).

**Architecture:** the server is mostly there (S3-06, `supabase/migrations/20261023031134_sends_storage.sql`, pgTAP
`060-sends-rls`, `070-storage-rls`): `sends` (read by sender, and by the recipient while not withdrawn and not
blocked), `create_send(p_id, p_recipient, p_payload)`, `withdraw_send(p_id)` (refused `55000` once saved),
`mark_send_saved(p_id)`, `dismiss_send(p_id)`, photo objects `sends/<send>/<media>.jpg` readable per `can_read_send`.
**One server migration in S7** (S7-03, below): photos staged before the send row exists (D77), `create_send` stamps
the sender's name (D80), `spots.from_username`. The client adds `src/utils/send-payload.ts` (pure freeze / thaw /
parse), local migration 7, `src/sync/sends.ts`, `src/components/SendSheet.tsx`, the Inbox's send rows,
`app/sent/index.tsx`, a tiny toast.

**Tech stack:** `@supabase/supabase-js` 2.118 (`storage.from(b).copy(from, to)`, `.remove(paths)`, `.download(path)`,
`.createSignedUrl(path, s)`, `rpc`), expo-sqlite 57, expo-file-system 57, zustand 5, expo-router 57. **No new
dependency.**

**Spec:** §1 (Send, D34 sentence), §3.2 (`sends`, storage paths), §3.3, §3.5, §5.4, §7 S7, D34, D37, D40, D41, D50,
D59; new D76–D82. **Diff base for the S7-08 review: `763a2a0`** (HARNESS: S6 verified).

## Global constraints

- `src/sync/sends.ts` functions take `(db?, client, uid, …)` and guard with `maySync` / `signedInAs`
  (`src/sync/account.ts`) like `friends.ts`: no session for `uid` → no call. No store or app singleton inside except
  where named (the integration test runs two riders in one process).
- **Only owned, backed-up spots are sent** (D78): every spot `owner_id = uid`, live, and no `sync_outbox` row (pending,
  failed or parked) for it or its live media. Another account's spot (S8) never shows Send.
- **The payload is only the frozen fields** (D40, list in Payload). Never `owner_id`, `legacy_json`, `updated_at`,
  `created_at`, `rev`, a user id, `file_path` or EXIF. `sender` is written by the server (D80).
- **A photo path is never trusted from a payload:** thaw rebuilds `sends/<sendId>/<media_id>.jpg` from the send id and
  a uuid-checked `media_id`; anything else in `path` drops that photo.
- **Photos exist before the row** (D77): copy every photo, then `create_send`; a recipient never reads a send with a
  missing photo. A failed copy or `create_send` removes that send's copied paths.
- Send, Save (any of the three), Dismiss and Withdraw are **single-flight**: Send by a `useRef<boolean>` checked
  synchronously in the sheet; the Inbox and Sent by a `useRef<Set<sendId>>` (S6 pattern); `saveSend` also keeps a
  module `Map<sendId, Promise>` so two callers share one save.
- Server errors are `console.warn`; the UI shows fixed copy only (Copy table). Server times through `toIso`.
- rpc args are `p_id` / `p_recipient` / `p_payload` (the feature texts write `{ id, recipient, payload }` informally).
- `npx expo lint && npx tsc --noEmit && npx jest --silent` green after every feature, zero `console.error`.

## Payload (S7-02) — `src/utils/send-payload.ts` (pure, no imports from `src/db` or `src/sync`)

Version 1, D40, frozen fields only:

```ts
export const SEND_PAYLOAD_VERSION = 1;
export interface SendPhoto { media_id: string; path: string /* 'sends/<send_id>/<media_id>.jpg' */; captured_at: string | null /* the day only, 'YYYY-MM-DD' (D46) */ }
export interface FrozenSpot {
  id: string;                 // the sender's spot id (dedupe on Pick; never a user id)
  name: string | null; generated_name: string | null;
  lat: number; lng: number;   // NO_LOCATION freezes as 0, 0 and thaws back to NO_LOCATION
  feature_types: FeatureType[]; stopped: boolean;
  natural_speed: number | null; // 0 stays 0; undefined → null
  notes: string | null;
  photos: SendPhoto[];        // primary first, then the detail grid's order; live media only
}
export interface SendPayload { v: 1; sender: { username: string; display_name: string | null }; spots: FrozenSpot[] }
```

- `freezeSend({ sendId, sender, spots, mediaBySpot }): SendPayload` — exactly the keys above (test with
  `Object.keys(...).sort()` equality), in the order given.
- `captured_at` is frozen as the **day only** (`'2026-10-13'`): D46 keeps capture times to the second off the server
  for others; the rider's own backup keeps the full value.
- `parseSendPayload(json: unknown, sendId): SendPayload` — throws `Error` naming the problem: `'send payload is not an
  object'`, `'unknown send payload version 2'`, `'send payload has no spots'`, `'send payload has more than 100
  spots'`, `'send spot 1 has no id'`, `'send payload has no sender username'` (must match
  `^[A-Za-z0-9_.]{3,20}$`). Lenient on content: an unknown feature type is dropped, `natural_speed` outside integer
  0–4 → null, non-finite lat/lng or |lat| > 90 or |lng| > 180 → NO_LOCATION, `stopped` non-boolean → false, a
  non-string name/notes/generated_name → null, a photo whose `media_id` isn't a uuid or whose `path` ≠
  `sends/<sendId>/<media_id>.jpg` is dropped; unknown keys ignored.
- `thawSend(payload, { sendId, uid, now, newId, spotIds? })` → `{ spots: Spot[], media: Media[], downloads: { path,
  localRelativePath, mediaId, spotId }[] }`: fresh ids per spot and photo; `owner_id = uid`; `created_at = updated_at =
  now`; `copied_from_send = sendId`; `from_username = payload.sender.username`; `primary_photo_id` = the first photo's
  new id; media `spot_id` remapped, `captured_at` kept, `file_path = localRelativePath =
  'photos/<newSpotId>/<newMediaId>.jpg'`, latitude/longitude = the spot's (no EXIF); `spotIds` filters by frozen id.
  `saveSend` drops photos whose download failed and resets `primary_photo_id` to the first one that arrived (or null).
- Size: at most 100 spots per send (D79), checked in `createSend` and in the sheet; 1 MB server cap is far above.

## Photo copy (S7-03) — in `createSend`

Per recipient (D76: one send row and one photo set each), in order:
1. `sendId = newId()` (client-side; passed to `create_send`).
2. For every photo of every spot: `client.storage.from('photos').copy('<uid>/<spot>/<media>.jpg',
   'sends/<sendId>/<media>.jpg')`, sequentially. The source is the rider's own pushed photo (`storagePath`).
3. Any copy error → `storage.from('photos').remove(<paths copied so far>)` (best effort, a remove error warns), no
   `create_send`, stop.
4. `rpc('create_send', { p_id: sendId, p_recipient, p_payload: freezeSend({ sendId, … }) })`; an error → remove all
   copied paths, stop.
5. Next recipient. Result `{ sentTo: FriendProfile[], failed?: { to: FriendProfile; message: string } }`: recipients
   before the failure stay sent (the sheet says so).

Before step 1: the D78 check; the sheet runs `await syncNow(db)` first (the sheet is not a `runExclusive` task) and
`createSend` re-reads the spots and media from SQLite and re-checks right before freezing (a spot edited between the
sync and the freeze waits again), throwing `NotBackedUpError(count)` when anything is still waiting. A parked row
(`photo missing`, 10 failures) counts as waiting; Profile already shows it as 'N changes not backed up' + Retry.

**Server migration** `supabase/migrations/20261024010000_sends_s7.sql` (append-only; RED pgTAP first), owned by
**S7-03** (it must run `npm run db:start` / `db:reset` / `test:db` / `db:stop`; S7-06 runs it again):
- **A staged object** = an object under `sends/<id>/` with `owner_id = auth.uid()::text` and **no** `sends` row with
  that id. `photos_insert`: also allowed for a staged object (WITH CHECK names `owner_id`, staging D77); the existing
  rule (sender's own, not saved, not withdrawn) still governs a send that exists. `photos_select` and
  `photos_delete`: also allowed for the caller's own staged objects (Storage's `remove` needs **delete and select**,
  `copy` needs insert and select, `storage-js` `index.d.mts:1705`/`:1321`); nobody else reads them (`can_read_send` of
  a missing send is false). `remove` checks `data.length` against the paths it asked for (0 rows is not an error).
- `create_send` (create or replace, same signature, body as shipped plus): refuses `42501` when an object under
  `sends/<p_id>/` has `owner_id is distinct from` the caller (a NULL owner refuses too); raises `22023` when the
  caller has no `profiles` row (`needs_username`); sets `p_payload.sender = { username, display_name }` from that row
  (D80), so a forged sender never reaches the recipient.
- `mark_send_saved` (create or replace): raises `55000` when the send is already saved (today it is idempotent via
  `coalesce`, so a second phone or a stale Inbox item would save duplicate copies).
- `spots.from_username text check (from_username is null or from_username ~ '^[A-Za-z0-9_.]{3,20}$')` — the
  `profiles_username_format` regex (`schema.sql:20`; citext keeps the case), so a mixed-case name never parks a push
  with `23514` (D80, a second phone shows 'From @ana'). Push maps `copied_from_send`, `from_username` (`sendSpot`
  names its columns, `push.ts:205`); pull maps them back, `from_username` only when the key is present (S7-03).
  **Deploy order:** the server migration before any client that pushes `from_username` (else PGRST204 stalls push);
  in the live checklist.
- `account-delete`: also removes the rider's staged leftovers (a killed app), found by a new service-role-only SQL
  function `staged_send_objects(p_uid) returns setof text` (Storage `list` can't find them without walking every
  send folder).
- pgTAP `100-sends-s7.test.sql` (new) + `070-storage-rls.test.sql`'s case 'nobody uploads into a send that does not
  exist' becomes 'a rider stages a photo for a send id nobody has used' (its inserts now set `owner_id`). Cases: stage
  ok, anon refused, staging with another `owner_id` refused; staged objects read only by their stager (recipient-to-be
  and strangers read none); the stager deletes them, another rider can't; another rider can't stage into an existing
  send's id; `create_send` refuses an id with another rider's (or a NULL-owner) staged object; after `create_send` the
  recipient reads the staged photos; `create_send` overwrites a forged `sender`, refuses a caller with no profile;
  `mark_send_saved` twice → `55000`; `from_username` 'Ana_B' accepted, 'a b' refused, stranger reads nothing;
  `staged_send_objects` not executable by `authenticated`.
- Rejected alternative: **a server-side copy function** (an Edge Function copying with the service role after
  `create_send`): a service-role key in a function, one more deploy (a live step), and the row exists before its
  photos. Also rejected: `create_send` first then copy (a recipient could open a send with photos missing).
- To check live in S7-06: the copied object's `owner_id` (either the caller or the source's owner: both are the
  sender, so the `create_send` check holds either way).

## Inbox (S7-03 data, S7-05 screen)

**Data.** `loadSends(client, uid)` → `sends` where `recipient = uid`, `saved_at is null`, `dismissed_at is null`
(withdrawn and blocked senders' sends are hidden by RLS), `order created_at desc`, pages of 500; each payload through
`parseSendPayload` (a bad one warns and is skipped). `loadAndApplySends(db, client, uid)` runs in the engine after the
friends load (same ticket / `maySync` / `signedInAs` guards) and calls `setItems(uid, 'send', …)`. The badge already
counts every kind by `created_at` (D75).

Defined inside `src/stores/inbox-store.ts` (`InboxItemBase` is not exported) and added to the `InboxItem` union:

```ts
export interface SendItem extends InboxItemBase { kind: 'send'; sendId: string; from: { username: string; display_name: string | null }; payload: SendPayload }
```

**Row.** '@ana sent you 3 spots' ('sent you a spot'), under it the first spot's label (D4) and town; thumbnail = the
first photo via `createSignedUrl(path, 600)` (none: no image). Buttons: 'Save all' · 'Save into a new hit list' ·
'Pick spots' · 'Dismiss'.
- **Pick spots** → a modal listing the frozen spots (label + town) with checkboxes, all checked; 'Save (2)'.
- **Dismiss** → Alert 'Dismiss these spots?' · "@ana won't be told." · Cancel / Dismiss → `dismissSend` → item off.

**Save** — `saveSend(db, client, uid, item, opts?: { spotIds?: string[]; newList?: boolean }, io = defaultPhotoIO)` →
`{ saved: number; failedPhotos: number; listId?: string }`, single-flight per send:
0. Take a new sends-load ticket (as `friends.ts` does), so a load already in flight can't put the item back.
1. `thawSend` (filtered by `opts.spotIds`).
2. Download each photo: `storage.from('photos').download('sends/<id>/<media>.jpg')` → `io.write` into
   `Paths.document/photos/<newSpotId>/<newMediaId>.jpg`. A failure leaves that photo out, keeps the spot, counts
   `failedPhotos` (warns).
3. and 4. run as **one `runExclusive` task** (never awaiting `syncNow`) with `maySync(db, client, uid)` re-checked
   inside, so a sign-out Remove, release or account switch can't interleave.
3. `rpc('mark_send_saved', { p_id })`. On an error: `signedInAs(client, uid)` false → "Couldn't save these spots.
   Try again." (item stays; 42501 also means "no session"); `55000` (saved already, e.g. on another phone) → files
   deleted, item leaves, 'Already saved'; any other error → re-read the row's `saved_at` (a lost response after the
   commit): set → go on to 4; not readable (withdrawn, blocked) → files deleted, '@ana took these spots back.', item
   leaves; else files deleted, "Couldn't save these spots. Try again.", item stays. Files are deleted with a new
   `PhotoIO.remove(filePath)` (default IO, `__mocks__` fake fs, the integration test's Node IO).
4. Insert through `src/db` (`insertSpot`, `insertMedia`; owner `uid`, so the migration 5 triggers append the outbox
   rows); `newList` → `insertHitList(db, { id: newId(), name: 'From @ana', kind: 'manual', created_at: now,
   updated_at: now, owner_id: uid, … })` (a full `HitList`, `hit-lists.ts:57`) + `addSpotsToList`. Then
   `reloadStoresQuietly(db)` and `removeItem(uid, 'send', id)`.

The feature text lists the rpc after the inserts; it runs **between the downloads and the inserts** so a withdrawal
racing the save (D40: withdraw until saved) can't leave copies of a withdrawn send, and a failed save leaves nothing
behind. A crash between 3 and 4 leaves the send saved with no copies (a few ms of local writes; accepted, review).
Picking spots finishes the send (D81): the others aren't offered again.

Lines at the top of the Inbox after a save: 'Saved 3 spots' · 'Saved 3 spots · 1 photo couldn't be downloaded' ·
'Saved 3 spots into From @ana'.

Saved copies: a normal owned spot (Edit present, Send present) with 'From @ana' under the title. 'From @name' is
frozen at save time (D80) and syncs with the spot.

## Integration test design (S7-06) — `src/__integration__/send.test.ts`

Two riders A, B (friends via `send_friend_request` + `respond_friend_request`), two node:sqlite DBs, Node `PhotoIO`
(S5-07 helper). A: 3 spots, one fixture photo each, `syncNow` until the outbox is empty. Cases:
1. `createSend` A → B (3 spots); A renames spot 1, soft-deletes spot 2, syncs. B `loadSends`: one send, 3 spots,
   spot 1's original name.
2. B `saveSend` → 3 owned spots with `copied_from_send` and `from_username` = A's username, 3 media rows, 3 files
   byte-equal to the fixture; B syncs (push ok); A's pull returns none of B's copies; B's second DB pulls them with
   `from_username`.
3. A sends 1 spot, A `withdrawSend` before B saves → B `loadSends` empty; B's download of `sends/<id2>/…` errors.
4. A `withdrawSend` on send 1 (saved) → `55000`.
5. Staging (D77): A copies, then `create_send` fails (B unfriended) → the staged objects are gone; B can't read a
   staged object of A's.
6. `create_send` with a forged `sender` → B sees A's real username.
Cleanup `deleteRiderAndPhotos` both. Run record (counts for `test:db` and `test:integration`) goes under 'As built'.
